## 背景
一个RAG的个人项目，既是一个demo，也是一个个人的内容存储工具，主要目的：
1. 存储自己的ai对话记录，可以很方便的本地查询（个人部署不外开放）
2. 作为rag的学习产出，部署成demo的演示
3. chunk逻辑由于只是存自己的对话记录，所以目前比较简单，**并且一切操作不涉及引入外部大模型**
4. 主要是反应rag的一些学习方向，比如：
   1. 适配业务属性的chunk方法，chunk段的上下文连接性，截断性
   2. embedding的模型选用，以及对应chunk的大小
   3. 多路检索的粗召回打分，尤其是knn检索的分数阈值调试
   4. 重排序：目前只做了rrf，其他的排序方法只不过是另一种业务下的选择，可能后续会考虑
## 介绍
架构方面：
1. 核心模块：go + es/mysql + qwen3.0-embedding-0.6B
2. go：
   1. 负责chunk方法管理，然后调用embedding模块产出es的存储内容
   2. 负责对es的召回内容做重排序打分
   3. 一些其他的系统性设计，比如接口，日志啥的
3. es/mysql：做存储，mysql做用户信息以及原始文本维护，es做文本以及向量存储
4. qwen3.0-embedding-0.6B：因为是我内网本地部署，所以选的小模型（我自己的服务器性能有限），而且因为是存储自己的信息，所以我直接拿我的nas+openwrt来部署的
## 思考：
1. go还是要负责chunk，chunk没有银弹，需要对不同的数据类型选取合适的方法，并且上下文的切分要需要考虑，一定程度上，尽可能的保留上下文最好
2. es的向量模型要尽可能优秀，并且在短文本上，很容易出现相似性混乱，所以对于向量召回的分数值需要设置阈值
3. 多路召回之后还需要做自己的排序，比如knn召回内容都会太多，并且有可能复杂一点说：bm25的召回和knn的召回可能正好合起来是一句话（有上下文关系），怎么去处理等等
4. 总结来说：
   1. chunk：强业务：业务属性比较多，主要看场景来决定chunk方法
   2. embedding：强算法：需要好的模型，并且短文本需要注意score
   3. 召回排序：半业务半算法：文本的关联性以及相关性
5. 如何评判rag：chunk/embedding/召回排序都需要大量数据做评测，然后动态调整参数以达到最好的水平，我目前能想到的参数：
   1. chunk的块大小，chunk的方法（可能有多个方法，不停的去试吧）
   2. embedding：这个跟模型有关了，我暂时不了解，直接看排名啥的吧或者自己验证模型的适配性，但是embedding的fetch处理参数会限制chunk大小
   3. 召回排序：knn的相关分数 + 召回的topk
6. rag跟业务场景还是很相关的，基本不想mysql/es这种可以稳定，所以rag应该给使用者提供一些动态能力，以供适配不同的场景，**总的来说，rag/llm/agent都是数据驱动**，其次也要考虑对数据的处理，比如：如果两个召回的片段有上下文关系，那么rag应该将其还原，交付尽可能完整的上下文
